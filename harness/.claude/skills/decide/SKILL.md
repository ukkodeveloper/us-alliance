# decide

인자: `$ARGUMENTS`

이 기록은 README 의사결정·AI 활용 섹션과 면접 답변의 원재료다. **사용자의 판단이 사용자의 말로** 남아야 한다. 기록이 많다고 좋은 게 아니다 — 핵심 결정은 과제당 4~6개.

## 세 종류

| ID | 언제 | 기록량 |
|---|---|---|
| **D-xx** 핵심 결정 | 되돌리기 비싸거나, 구조에 영향을 주거나, 면접에서 설명할 가치가 있는 것 | 전체 프로토콜 |
| **N-xx** 메모 | 가정 하나, 엣지케이스 처리 여부, 축소선 이동, 리뷰 지적 수용 등 | 한 줄 |
| **X-xx** 거절 | 사용자가 AI 제안을 거절·수정 | 두세 줄 |

어느 쪽인지 애매하면 N으로 시작하고, 나중에 중요해지면 D로 올린다.

## D 프로토콜

1. **맥락** 1~2줄, 관련 요구사항 `R-n`
2. **대안 2~3개**: 장점 / 비용 / 이 과제에서의 위험. `design-patterns.md`의 신호·예외로 근거. 하나에 `AI 추천`과 이유. "하지 않음"이 합리적이면 대안에 포함
3. **사용자 선택과 이유**: 이유는 **사용자 원문을 따옴표로 인용**한다. 다듬거나 보충하지 않는다. 사용자가 이유 없이 고르면 한 번만 묻고, 그래도 없으면 이유를 비워 두고 출처를 `AI 제안 → 수용`으로 적는다
4. **사이드 이펙트 검토 (AI)**: 다른 결정과의 충돌, 남은 시간, 공통 모듈 영향, 위험. 문제가 있으면 알리고 유지/수정을 묻는다
5. 기록 (시각 포함: `date "+%H:%M"`)

```
### D-03 [패턴] 주문 상태 분기 방식 (11:42)
- 맥락: R-3 주문 상태 4종에 따라 화면이 다름
- 대안: A) 삼항 중첩  B) switch + neverCheck (AI 추천: 상태 추가 시 누락을 컴파일러가 잡음)  C) ts-pattern
- 선택: B — "상태가 늘어날 게 뻔하고 누락되면 빈 화면이 나옴. ts-pattern은 이 정도엔 과함"
- 출처: AI 제안 → 수정 (C 배제는 사용자)
- 사이드 이펙트: 상태별 컴포넌트 4개 → 파일 수 증가, 수용
- 근거: design-patterns P7, code-style S8
```

## N 형식

```
- N-07 [요구사항] 수량 상한 없음 → 재고 수로 제한 — "재고보다 많이 담기는 건 버그로 보일 것" (AI 제안 → 수용) 11:05
```

## X 형식

판단력의 가장 강한 증거이므로 대화 중 사용자가 AI 제안을 거절하면 바로 기록한다.

```
### X-02 [리뷰] 장바구니 전역 상태화 제안 거절 (14:20)
- AI 제안: 장바구니를 Zustand 스토어로
- 이유: "이 페이지 안에서만 쓰임. 라이브러리 추가 비용이 더 큼"
- 대신: 페이지 지역 상태 + composition
```
