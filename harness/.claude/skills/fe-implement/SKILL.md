# 4단계: 구현

입력: `notes/plan.md`, `notes/decisions.md`, progress.md. 아래 `<R>`은 `assignments/<과제명>/repo`.

## 작업 트리

- 모든 에이전트가 **같은 작업 트리**(`<R>`)에서 일한다. 소유 파일이 겹치지 않으므로 충돌이 없고, worktree마다 의존성 설치·dev 서버를 따로 두는 비용이 없다. (fe-task는 git이 아니라 Agent의 worktree 격리도 쓸 수 없다.)
- 소유 파일이 겹치는 단위는 병렬로 돌리지 않는다.
- dev 서버는 0단계에서 띄운 하나를 공유한다. 의존성 설치 후에는 재시작한다.

## 그룹 루프

1. **준비**: 그룹에 의존성 추가 단위가 있으면 먼저 처리·커밋한다.
2. **병렬 구현**: 그룹의 단위들(최대 3개)에 `fe-implementer`를 한 메시지에서 동시에 띄운다. 프롬프트에 넣을 것:
   - 단위 명세 전문, 소유 파일 목록 (외에는 수정 금지)
   - 관련 D/N 원문, **해당 단위의 G 원문**
   - `<R>` 절대경로, 패키지 매니저, 검증 명령, 기존 테스트 명명 규칙
3. **메인 점검** (결과가 올 때마다):
   - `git -C <R> status --short`로 소유 파일 외 변경이 없는지 확인
   - diff를 훑어 범위 초과·AI 냄새(`references/ai-smell.md`) 제거
   - 보고서의 "결정 필요" → `decide`
4. **QA**: 그룹의 단위가 모두 모이면 `.claude/skills/fe-qa/SKILL.md`를 따라 **그룹 단위로** QA한다.
5. **커밋**: 사용자가 승인하면 plan 순서대로 단위마다:
   ```
   git -C <R> add <소유 파일들>
   git -C <R> diff --cached --name-only   # 소유 파일과 정확히 일치하는지
   git -C <R> commit -m "<plan의 메시지>"
   ```
   그다음 통합 단위를 커밋한다. 리뷰나 QA에서 바뀐 이유가 있는 커밋은 본문에 이유를 한 줄 적는다. attribution·co-author는 넣지 않는다.
6. plan.md 체크, 보드 "계획" 진행 상태, progress.md 시각을 갱신한다.

## 시간

그룹이 끝날 때마다 지연을 확인한다. 15분을 넘으면 축소선 조정을 제안한다 (`decide` N `[범위]`).

## 하지 말 것

- 사용자 승인 없이 커밋, 여러 단위를 한 커밋으로 합치기
- 에이전트가 덧붙인 범위 밖 기능을 plan 없이 수용
