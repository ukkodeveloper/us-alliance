# 2단계: 전략

입력: `notes/assignment.md`, 보드 "이해" 확정 내용, `notes/decisions.md`, `notes/company.md`, `references/design-patterns.md`, `references/code-style.md`.

## 결정 목록

**실제로 갈림길이 있는 것만** 고른다 (보통 3~5개 D). 신호가 없는 항목은 "기본값"으로 N 한 줄.

| 영역 | 처음부터 / 스타터 | 주어진 레포 |
|---|---|---|
| 스택 | 프레임워크, 서버 상태, 스타일링, 폼. 회사 스택은 참고만, 근거 없으면 최소 구성 | 기존 유지가 기본. 추가 라이브러리만 결정 |
| 디렉토리 | P1 적용 범위 | P1 예외: 기존 최상위 유지, 새 기능 폴더 안에서 colocation |
| **데이터 소스** | 실 API / MSW / 로컬 fixture. 에러·빈 상태를 재현할 방법 포함 | 기존 방식. 백엔드가 없으면 동일하게 결정 |
| 상태·비동기 | P8 경계 배치, P9 서버/클라 상태 | 기존 방식과의 일관성 vs 개선 |
| 핵심 패턴 | 요구사항 중 P2~P14 신호가 있는 곳 | 동일 |
| **테스트 환경** | 러너(Vitest+RTL 기본), 설정 단위 필요 여부 | 기존 러너·위치·명명 따름. 없으면 추가 여부 결정 |

토스 OSS 라이브러리(suspensive, overlay-kit 등)는 패턴의 **근거**일 뿐, 도입은 P0-5 기준으로 따로 판단한다.

## G 반영

결정마다 관련 G가 있으면 대안 비교의 첫 기준으로 삼는다. G가 code-style·design-patterns와 다른 방향을 요구하면 G를 따르고 그 사실을 D에 적는다.

## D마다

`.claude/skills/decide/SKILL.md`의 D 프로토콜. 사이드 이펙트 검토에서 특히:
- 앞선 결정과 충돌하지 않는가
- 남은 시간 안에 가능한가 (설정·학습 비용 포함)
- 주어진 레포의 공통 모듈을 바꾸게 되는가
