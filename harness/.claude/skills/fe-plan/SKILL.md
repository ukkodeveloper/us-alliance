# 3단계: 커밋 계획

**커밋 목록이 곧 plan이다.** `git log`만 읽어도 사고 흐름(설정 → 계약 → 핵심 로직 → UI → 상태·엣지 → 다듬기)이 재구성되도록 설계한다.

입력: 보드 "이해" 확정 내용, `notes/strategy.md`, `notes/decisions.md`, progress.md(남은 시간).

## 단위 명세

```
### U3 feat(order): 주문 상태별 화면 분기
- 요구사항: R-3 / 평가 기준: G-2 / 결정: D-03
- 소유 파일: src/domains/order/components/OrderStatusView.tsx (생성), OrderStatusView.spec.tsx (생성)
- 의존: U1, U2 / 그룹: B
- 수용 기준: 상태 4종 각각 올바른 화면, 알 수 없는 상태 → ErrorBoundary
- 검증: 단위 테스트 4개 / e2e: 없음 (핵심 흐름 F1에 포함)
- 예상: 15분 / 우선순위: Must
```

## 규칙

1. **한 커밋 = 한 가지 이유.** 리뷰어가 5분 안에 읽을 크기.
2. **소유 파일은 단위 간에 겹치지 않는다.** 공용 파일(라우트 등록, 도메인 `index.ts`)은 메인이 맡는 통합 단위로 분리하고, **통합 단위는 그것이 import하는 단위들 뒤에** 둔다 → 모든 커밋 시점에 빌드가 깨지지 않는다.
3. **의존성 추가(`package.json`, 설치)는 그 그룹이 시작되기 전 단위로** 먼저 커밋한다.
4. 병렬 그룹은 동시에 최대 3개. 같은 그룹 안에서는 의존이 없어야 한다. 단위가 짧거나 얽혀 있으면 순차.
5. 계약(타입, API 함수, 쿼리 옵션)은 첫 그룹에서 먼저 커밋한다.
6. 테스트는 해당 로직과 같은 커밋에. 테스트 환경이 없으면 "테스트 환경 설정" 단위를 앞에 둔다. 주어진 레포는 기존 테스트 위치·명명을 따른다.
7. 처음부터 모드: `chore: 프로젝트 초기 설정` → (선택) `chore: lint·format 설정 추가` 순으로 시작.
8. 기존 코드 수정은 `refactor(...)` / `fix(...)` 단위로 분리하고 D/N을 연결한다.
9. **e2e 핵심 흐름**을 2~3개(F1~F3)만 정하고, 흐름이 완성되는 단위에 붙인다. 모든 단위에 e2e를 쓰지 않는다.

## G 커버리지

모든 G가 최소 한 단위(또는 README 섹션)에 연결되어야 한다. plan.md 끝에 표로 남긴다:

| G | 대응 단위 / 산출물 | 제출물에서 드러나는 곳 |
|---|---|---|

연결되지 않은 G가 있으면 계획을 승인받기 전에 단위를 추가한다. 축소선을 그을 때 **G에 연결된 단위는 축소 대상에서 제외**한다.

## 시간

- 단위 예상 합계 + 그룹당 QA 7분을 남은 구현 예산과 비교한다.
- 넘으면 **축소선**: 선 아래(Nice, 일부 Should)는 시간이 남을 때만 → `decide` (N, `[범위]`).

## 산출물과 Gate

- `notes/plan.md` (단위 명세 전체)
- 보드 "계획" 섹션: 그룹별 커밋 타임라인, 단위 카드, 진행 체크, 축소선
- 사용자가 전략과 계획을 함께 승인 → progress.md 기록 → `/compact` 권장
