# 과제 평가 기준표 (면접관 관점)

`fe-readme` 이후 `fe-evaluate` 단계에서 사용. **제출물만 보는 새 맥락의 평가자**가 이 표로 채점하고, 지적마다 사용자가 수정/수용을 결정한다.

## 근거

**우선순위: 과제가 명시한 평가 기준(G) > JD 신호 > 이 표.** G가 있으면 평가 리포트 맨 앞에서 G별로 먼저 채점하고, G에 해당하는 이 표의 항목은 ★★★로 올린다.

이 표는 회사와 무관한 **공통 기준**이고, 과제마다 `notes/company.md`(JD 기반 회사 프로필)의 "가중할 신호"로 우선순위를 조정한다.

| 출처 | 역할 |
|---|---|
| **FF** Code Quality ([링크](https://frontend-fundamentals.com/code-quality/code/)) | 코드 품질 공통 기준: 가독성·예측 가능성·응집도·결합도와 그 트레이드오프 |
| **공통 FE 과제 축** (출처 예: [토스 지원 가이드](https://toss.tech/article/frontend-apply-without-resume)) | 회사와 무관하게 과제에서 공통으로 보는 축: 모듈화·코드 품질 / 디렉토리 구조 / 엄격한 TS / 제품 완성도 / 읽기 쉬운 커밋 / README. "화려한 기술보다 수정하기 쉬운 코드에 대한 고민" |
| **회사 프로필** `notes/company.md` | JD의 핵심 역량·우대사항 → 항목별 가중. 예시(가상의 회사): 모바일 화면(A4), 스스로 문제 정의(C1), 레거시 개선·점진적 이관(C4), 단순한 추상화(C2) |

## 모드별 적용

| 항목 | 처음부터 | 주어진 레포 |
|---|---|---|
| A2 실행 재현성 | 스캐폴딩·설정까지 평가 | 기존 실행 방식을 깨지 않았는지 |
| B6 스타일 일관성 | 전체가 code-style 준수 | 기존 lint/formatter 준수 + 새 코드는 code-style |
| C4 기존 코드 대응 | **초기 설정 판단**으로 대체: 스택·구조·도구 선택이 과제 규모에 맞고 근거가 있는가 | 변경 범위 최소화 + 문제 발견·점진적 개선안 |
| E1 커밋 | 초기 설정 커밋이 분리되어 있는가 | base 이후 커밋만 평가 |

## 채점 방식

- 항목마다 **미흡 / 기대 / 탁월** 중 하나 + **근거(file:line, 커밋 해시, README 섹션)** 필수. 근거 없는 평가는 무효.
- 우선순위: ★★★ 탈락을 가르는 항목 / ★★ 차별화 항목 / ★ 가산 항목. 회사 프로필의 가중 신호에 해당하는 항목은 한 단계 올려 본다.
- 지적마다 `수정 비용(분)`과 `수정 시 이득`을 함께 적는다.

## 레드 플래그 (하나라도 있으면 즉시 수정)

- 실행 실패, 콘솔 에러·경고
- `any`, 근거 없는 `as`, `// @ts-ignore`
- 쓰이지 않는 파일·export·의존성
- 주석 (지시 주석 제외)
- 공통 모듈의 이유 없는 변경
- 거대 커밋, `fix`/`update` 같은 의미 없는 메시지, Claude co-author
- README에 적었지만 코드에 없는 내용 (또는 그 반대)

## 평가 리포트 형식

```
[B4 결합도] 미흡 → 기대 목표
- 근거: src/domains/order/hooks/useOrderPage.ts:12-80 (쿼리 파라미터 5개 + 제출 로직)
- 문제: 파라미터 하나만 바뀌어도 사용처 4곳 영향
- 제안: 파라미터별 훅 분리 (FF "책임을 하나씩")
- 수정 비용: 20분 / 이득: B1·B4 동시 개선
- 결정: [ ] 수정  [ ] 수용(이유: ____)
```

수용 결정과 그 이유는 `decide`(N `[리뷰]`)로 기록한다 → README "한계" 섹션의 재료.
