FE 과제 파이프라인

5시간짜리 프론트엔드 과제를 AI와 함께 수행하는 방법. AI는 분석·구현·검증을 맡고, 해석과 선택은 내가 한다. 그 판단이 제출물에서 읽히도록 만드는 것이 이 체계의 목적이다.

목표

무엇으로 평가받는가

최종 목표는 AI를 잘 활용하되, 판단 근거가 분명하고, 안정적이며, 과하지 않은 서비스를 만드는 것. 제출물은 세 축으로 읽힌다.

완성도받자마자 실행되고, 요구사항과 로딩·에러·빈 상태가 처리되어 있는가. 시간 대부분을 구현에 쓴다.
차별성기능을 더 넣는 것보다 AI 냄새를 걷어내고, 사용자 관점 개선 1~2개를 근거와 함께 넣는 것.
고민가정·선택·포기한 것이 README, 테스트 이름, 커밋에서 확인되는가. 면접에서 내 말로 설명되는가.

최우선

회사가 명시한 평가 기준

과제 안내에 "이런 점을 중점적으로 봅니다"가 있으면 0단계에서 원문 그대로 뽑아 G-1, G-2…로 번호를 붙인다. G는 이 체계의 모든 규칙보다 우선한다.

단계G가 쓰이는 방식
0 시작원문 인용, 지키는 방법 해석, 내 규칙과의 충돌 확인(충돌하면 G를 따르고 D로 기록)
1 이해보드 맨 위에 표시. G와 직결된 요구사항은 Must
2 전략결정마다 관련 G를 대안 비교의 첫 기준으로
3 계획모든 G가 최소 한 단위에 연결되어야 승인. G에 연결된 단위는 범위를 줄일 때도 빼지 않음
4 구현구현 에이전트가 단위의 G 원문을 받고, 보고서에 대응 방법을 적음
5 리뷰 · 7 평가리뷰어와 면접관이 G별 충족 여부를 가장 먼저 채점
6 README기준마다 제출물의 어디에서 확인할 수 있는지 연결

잊히지 않게 하는 장치: G 목록은 progress.md 상단에 있고, 메시지마다 hook이 진행 중 과제의 G를 맥락에 넣는다. /compact 뒤에도 사라지지 않는다. 회사가 주석을 요구하면 notes/allow-comments로 주석 검사를 끈다.

판단의 증거

AI를 썼지만 판단은 내가 했다는 것을 보여주는 장치

결정은 decide로 세 종류로 남긴다. 많이 남기는 게 목적이 아니다. 핵심 결정은 과제당 4~6개.

ID언제기록
D 핵심 결정구조에 영향, 되돌리기 비쌈, 면접에서 설명할 가치맥락 → 대안 2~3 + AI 추천 → 내 선택과 이유(원문 인용) → AI의 사이드 이펙트 검토
N 메모가정 하나, 엣지케이스 처리 여부, 축소선 이동, 리뷰 수용한 줄
X 거절AI 제안을 거절하거나 고쳤을 때AI 제안 → 내 이유 → 대신 한 것
 
flowchart LR
  A[결정이 필요한 지점] --> B[AI: 대안 2~3 + 추천]
  B --> C[나: 선택 + 이유]
  C --> D[AI: 사이드 이펙트 검토]
  D -->|문제 없음| E[decisions.md]
  D -->|충돌·시간 초과| C
  E --> F[README 의사결정 · AI 활용]
  E --> G[테스트 이름 · 커밋 본문]

출처 표기

사용자 발의 / AI 제안 → 수용 / 수정 / 거절. README의 역할 구분이 이 표기에서 나온다. 비율을 맞추려고 거절을 만들지 않는다.

제출물에서 확인 가능하게

가정은 테스트 이름으로 고정하고, 리뷰 반영 커밋 본문에 이유를 한 줄 적는다. README의 주장은 테스트·커밋 링크로 연결한다.

새 맥락의 검증

리뷰어와 평가자는 결정 기록을 보지 못한다. 그들이 의도를 못 읽었다면 코드나 README가 아직 설명하지 못하고 있다는 뜻이다.

면접 리허설

평가자가 뽑은 질문 5개에 내가 먼저 답하고, AI는 코드 근거로 맞는지 짚는다. 결국 증거는 내 설명이다.

코드 스타일

토스 커뮤니티 기준, 근거와 예외까지

규칙은 두 문서로 나뉜다. code-style.md는 어떻게 쓰는가(S1~S36), design-patterns.md는 언제 어떤 구조를 고르는가(P0~P14). 회사가 토스가 아니어도 같은 기준을 쓴다.

적용 순서내용
1주어진 레포의 lint · formatter · tsconfig · 테스트 명명 · 커밋 컨벤션
2code-style · design-patterns (도구가 정하지 않은 모든 것)
3일반 관례

모든 규칙은 같은 형식을 따른다. 쓰지 않는 조건이 성급한 추상화를 막고, 예외는 어떤 상황에서 왜 다르게 하는지를 적는다.

규칙 / 근거 [FF] [OSS:repo] [toss.tech] [간접] [내 판단] / 쓰지 않는 조건 / 예외(상황 → 방법 → 이유) / 예시 / 면접 한 줄

P0 추상화 원칙

변경을 예측한 만큼만 추상화한다. 사용처마다 달라질 여지가 있으면 중복을 허용하고, 함께 안 바뀌면 오류가 나는 것만 공통화한다.

대표 규칙

function 선언 + named export, type 우선, 불가능한 상태는 Discriminated Union, union 분기는 switch + never, 훅 반환은 1개 값 / 2개 튜플 / 3개 이상 객체, 클릭 가능한 것은 button이나 a.

대표 패턴

도메인 colocation과 도메인 간 import 금지, composition 먼저 Context는 나중, Suspense·ErrorBoundary 경계, render props로 데이터 경계 드러내기, 결과가 필요한 오버레이는 Promise.

토스와 다르게 정한 것

주석 금지는 내 규칙이다. 토스 OSS는 JSDoc과 "왜" 주석을 쓴다. 이 차이와 reduce 대신 for, 커버리지 100% 같은 라이브러리용 규칙의 제외 이유를 문서에 남겼다.

안전장치

규칙을 사람 기억에 맡기지 않는 것들

장치하는 일
주석 검사 hook파일을 수정할 때마다 TypeScript 파서로 이번에 추가한 줄의 주석만 찾는다. 문자열·JSX 텍스트·URL은 오탐하지 않고, 기존 코드의 주석은 건드리지 않는다. 도구 지시 주석은 예외.
commit-msg hookAI attribution 줄을 막고, Conventional Commits 형식을 검사한다. 레포 컨벤션이 다르면 형식 검사만 끈다.
평가 기준 주입 hook메시지마다 진행 중 과제의 현재 단계와 G 목록을 맥락에 넣는다.
attribution 설정Claude Code의 커밋·PR attribution을 끈다.
base 커밋 · 기준선원본을 고정해 내 변경만 diff로 보이게 하고, 원래 실패하던 것을 분리해 둔다.
소유 파일병렬 에이전트는 자기 파일만 수정하고 커밋하지 않는다. 메인이 스테이징을 소유 목록과 대조한다.

내가 검토할 것

code-style.md와 design-patterns.md는 내 스타일의 기준이므로 직접 검토가 필요하다.
  • [내 판단], [간접] 태그가 붙은 규칙과 숫자 임계값("2곳 이상", "3단계")을 받아들일지
  • 토스 안에서 갈리는 규칙(function vs 화살표, interface 혼용, 테스트 명명)에서 고른 쪽이 맞는지
  • 각 규칙의 "쓰지 않는 조건"과 "예외"가 내가 실제로 판단하는 방식과 맞는지
  • "면접 한 줄"을 내 말로 바꿀 수 있는지
  • 처음 과제를 돌린 뒤 시간 배분과 gate 개수가 적당했는지 → /fe-tune review로 정리
