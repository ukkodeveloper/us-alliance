# 0003. 발행 API는 순수 함수로 계획하고 순차 실행

- 상태: 채택
- 출처: AI 제안 → 수용

## 맥락

발행 모달 하나가 공개 상태 변경, 예약 일정 생성·수정·삭제, 알람 생성·수정·삭제를 다룹니다. 서로 다른 API이고 트랜잭션이 없습니다. 같은 "공개"를 골라도 현재 서버 상태(이미 공개인지, 예약 중인지, 알람이 있는지)에 따라 불러야 할 API가 달라집니다.

## 대안

- A. 순차 호출. 실패하면 에러를 보여주고 모달을 유지한다. 재시도할 때는 서버 상태를 다시 읽어 남은 단계만 수행한다
- B. 실패하면 이전 상태로 롤백한다
- C. 병렬 호출

## 결정

A. 롤백용 API가 모든 단계에 있지 않고, 서버 상태를 다시 읽어 계획하면 재시도가 멱등에 가까워집니다.

"서버 상태 + 사용자가 고른 옵션 → 호출할 단계 목록"을 순수 함수 `createPublishPlan`으로 분리하고, `runPublishPlan`이 그 목록을 순서대로 실행합니다. 계획은 변화가 있는 단계만 만듭니다. 예를 들어 예약 시각이 같으면 일정 수정을 부르지 않습니다.

## 결과

- 상태 조합을 단위 테스트로 고정했습니다(`src/domains/contents/publish/publishPlan.spec.ts`). 중간 실패 뒤 재시도 시 남은 단계만 남는 경우도 테스트합니다.
- 부분 성공 상태가 잠깐 화면에 보일 수 있습니다. 에러 문구로 안내합니다.
- 리뷰에서 "이미 공개된 콘텐츠의 예약 알람이 재발행 때 즉시 발송되는" 조합을 찾아 고쳤습니다(`39619e4`).
- 그 수정 뒤에는 "이미 공개였나"를 재시도 시점의 서버 상태로 판정했는데, 중간 실패 뒤에는 이미 공개로 바뀌어 있어 원래 의도(지금 발송)가 사라졌습니다. 그래서 이 판정만은 모달을 연 시점의 상태로 고정합니다(`wasPublicWhenOpened`).
